# Sprint r-7 — `sc-decision-schema` crate and model catalog

Owner decisions 2026-11-07 (plan.md "Owner decisions 2026-11-07", items 1–4
and 7). Governing ADRs: ADR-SAG-0030 (whole ADR) and ADR-SAG-0031's
"Storage schema" subsection, both inserted **Proposed** by the plan PR and
flipped by this sprint.

## Outcome

Every decision type has one home, `sc-decision-schema`, a published,
data-only crate above `sc-agent-types`. It holds the versioned decision
schema (question and answer payload), one serde request and response struct
per Jev API call known today, the Haiku/Luna input/output mapping on the same
schema, the per-model-family variant mechanism for future local decision
models, and the session-log SQLite schema with its `fields{}` projection.
`sc-agent-types` keeps what every agent kind shares (ids, errors, secrets,
git, cancel, the observability port, the backend catalog) and gains a model
catalog: an open `ModelId` enum and `latest(alias)` lookup, overridable from
`check.toml`. No wire byte, digest, stdout golden or session document byte
changes.

## Layering (decided; ADR-SAG-0030)

```text
sc-agent-types        ids, JevError/ErrorCode, ScAgentErrorResponse, BackendId + BACKENDS,
  (below)             ModelId/ModelFamily/ModelAliases, Sha256Digest, CancelToken,
                      ResolvedApiKey (secret), observability::v2 port (obs), git (git),
                      schema::subjects
sc-decision-schema    QuestionId, ChoiceId, Question, ChoiceAnswer, CanonicalJudgePayload,
  (above)             PayloadBundle, canonical_json_bytes, QuestionAnswer, JudgeOutcome,
                      JudgeRequest, LlmWireContext, JudgeBackend, BackendCapabilities,
                      Attestation, BackendAttestation, EqualInputRecord, MultiBackendMode,
                      DecisionSchemaId + versions, jev::v1, llm::v1, variants, session_log;
                      test_util::MockJudgeBackend (test-util)
```

- **Data-only** means the dependency set: `sc-agent-types`
  (`default-features = false`, core only), `serde`, `serde_json`. No HTTP,
  git, process, file or logging dependency and no I/O in `src/`. The
  `JudgeBackend` trait moves with the types its signatures name (a trait
  cannot sit below `JudgeOutcome`); it adds no dependency.
- **Moved, not copied.** `sc-agent-types` loses the `judge` and `payload`
  modules, `QuestionId`, `ChoiceId` and `test_util`; it re-exports none of
  them. Its `judge` and `test-util` features are deleted (nothing is
  published, so no deprecation path). Every call site imports from
  `sc_decision_schema`.
- **`BackendId` vs `ModelId`.** `BackendId` is how we call (Jev API,
  Anthropic API, OpenAI API); `ModelId` is which model. Today's id spellings
  `anthropic_haiku` / `openai_luna` are kept as is (serde, CLI, `check.toml`
  compatibility); renaming them is not in scope.

## Split considered (kept as one sprint)

The model catalog (D8) was considered as its own sprint and kept here: D4
(`CheckRequest.model: &ModelId`) and D6 (`schema_for(ModelFamily)`) name its
types, and its `sc-jev-check` factory/config edits sit in the same files as
D2's import changes, so a separate sprint would either run first (one more
wave on the critical path) or share every owned path with r-7. The session-log
schema (D7) is data-only and has no caller until r-6. Every deliverable has
its own `req:` row below, so none can slip while the sprint claims success.

   or retyped field, or a changed meaning, bumps it.
3. **The version lives outside the hashed bytes.** It is never a key of
   `CanonicalJudgePayload` and never part of `PayloadBundle::bytes()`, so
   `prompt_sha256` and the Rust/Python cross-implementation fixture stay
   byte-identical. It is carried by the sc-agent-owned wrappers around the
   payload: the session-log row (`decision_schema`, D7) and, from r-6, the
   session document. It is not sent to Jev, Anthropic or OpenAI (their
   bodies follow their own schemas, D4/D5).

### D7 — Session-log storage schema and `fields{}` projection (REQ-SAG-0146; ADR-SAG-0031 "Storage schema")

Owner decision 2026-11-07 item 5: the SQLite schema is authoritative; the
JSONL "projection" is the `fields{}` object of one sc-observability v2 log
line (ADR-SAG-0013: no bespoke writer); a loader reads `fields{}` into the
tables. The earlier "flat top-level, no nesting" wording is superseded. r-7
defines the schema and types; **r-6 emits them**. No SQLite dependency or
writer lands in A.1.

1. `crates/sc-decision-schema/src/session_log/schema.sql` (the DDL,
   `pub const SESSION_LOG_DDL: &str = include_str!(...)`),
   `SESSION_LOG_SCHEMA_VERSION: u32 = 1`, `COLUMNS` (the projection's key
   list, in order), `RowContext` (the values every row carries),
   `SessionLogRow` (private fields, one constructor per outcome:
   `SessionLogRow::ok(RowContext, DecisionAnswers)` and
   `SessionLogRow::failed(RowContext, ErrorCode)`; signatures under
   "Explicit code samples"),
   `SendOutcome { Ok, Failed }` (serde `ok` / `failed`),
   `SessionLogRow::to_fields() -> serde_json::Map<String, Value>` and
   `SessionLogRow::try_from_fields(&Map) -> Result<Self, JevError>`
   (unknown key, missing key or wrong type is `INPUT_INVALID`).

   ```sql
   -- schema_version 1. Authoritative; see docs/sc-decision-schema/session-log-schema.md.
   CREATE TABLE sessions (
     session_id          TEXT PRIMARY KEY,        -- ULID (r-6)
     session_created_at  TEXT NOT NULL,           -- RFC 3339 UTC, ms
     repo                TEXT NOT NULL,           -- main repo root, else calling folder (absolute)
     project             TEXT                     -- caller text; NULL when absent; not scrubbed
   );
   CREATE TABLE questions (
     prompt_sha256    TEXT PRIMARY KEY,           -- SHA-256 of the canonical payload bytes
     decision_schema  TEXT NOT NULL,              -- DecisionSchemaId, e.g. canonical.v1
     question_ids     TEXT NOT NULL,              -- JSON array, payload order
     first_seen_at    TEXT NOT NULL               -- loader: ts of the first row for this digest
   );
   CREATE TABLE answers (
     answer_id       TEXT PRIMARY KEY,            -- ULID, one per send
     schema_version  INTEGER NOT NULL,            -- SESSION_LOG_SCHEMA_VERSION of the row
     session_id      TEXT NOT NULL REFERENCES sessions(session_id),
     prompt_sha256   TEXT NOT NULL REFERENCES questions(prompt_sha256),
     request_sha256  TEXT,                        -- SHA-256 of the exact body sent; NULL when no body was built
     ts              TEXT NOT NULL,               -- RFC 3339 UTC, ms; when the send finished
     operation       TEXT NOT NULL CHECK (operation IN ('judge','ask')),
     backend         TEXT NOT NULL,               -- BackendId: how we called
     model_id        TEXT NOT NULL,               -- ModelId string: which model (never NULL)
     send_outcome    TEXT NOT NULL CHECK (send_outcome IN ('ok','failed')),
     error_code      TEXT,                        -- ErrorCode id; NOT NULL iff failed
     answers_json    TEXT,                        -- DecisionAnswers JSON; NOT NULL iff ok
     CHECK ((send_outcome = 'ok') = (error_code IS NULL)),
     CHECK ((send_outcome = 'ok') = (answers_json IS NOT NULL))
   );
   CREATE INDEX answers_by_question_model ON answers (prompt_sha256, model_id);
   CREATE INDEX answers_by_request        ON answers (request_sha256);
   CREATE INDEX sessions_by_repo_project  ON sessions (repo, project);
   ```

2. **Projection.** One send is one log line; its `fields{}` object has
   exactly the `COLUMNS` keys: `schema_version`, `answer_id`, `session_id`,
   `session_created_at`, `repo`, `project`, `prompt_sha256`,
   `decision_schema`, `question_ids`, `request_sha256`, `ts`, `operation`,
   `backend`, `model_id`, `send_outcome`, `error_code`, `answers_json`.
   Nullable columns are present with `null`. `question_ids` is a JSON array
   and `answers_json` a JSON object (the SQLite columns hold the same JSON as
   text). The key is `send_outcome`, not `outcome`, so it never collides with
   the v2 envelope's own `outcome`. `ts` is the row's time; the envelope
   `timestamp` is write time and the loader ignores it. A loader inserts
   `sessions` and `questions` with `INSERT OR IGNORE` (deriving
   `first_seen_at` from `ts`) and `answers` with `INSERT`; the projection is
   lossless with respect to the schema.
3. **Rules.** No secret, payload text, prompt text or raw response body in
   any column (NFR-SAG-0002); `answers_json` holds only typed answers.
   `repo` is the only path column. `project` is caller text, stored as
   given and not scrubbed (documented). Adding or renaming a column, or
   changing a type or nullability, bumps `SESSION_LOG_SCHEMA_VERSION` with a
   migration note in the schema document.
4. `docs/sc-decision-schema/session-log-schema.md`, titled "Session log
   storage schema (SQLite, authoritative)": the DDL (copied from
   `schema.sql`, checked equal by `test_session_log_doc_matches_ddl`), the
   projection rule, a column reference with nullability, the loader rule.
5. Golden fixture `tests/fixtures/decision-schema/session-log/fields.jsonl`:
   one `fields{}` object per line — an `ok` judge, a `failed` judge with a
   body (`request_sha256` set), a `failed` judge before any body was built
   (`request_sha256: null`, `model_id` set), an `ok` ask, and a row with
   `project: null`.

### D8 — Model catalog in `sc-agent-types` (REQ-SAG-0147, REQ-SAG-0148)
